Yes — Azure **AKS**. The key idea is that every Kubernetes platform ultimately adds a **context** to your kubeconfig, normally `~/.kube/config`. After that, the universal command is:

```bash
kubectl config get-contexts
kubectl config use-context <CONTEXT-NAME>
```

### Kubernetes context cheat sheet

| Platform       | Add/get cluster credentials                                                 | Switch context                                         |
| -------------- | --------------------------------------------------------------------------- | ------------------------------------------------------ |
| Docker Desktop | Usually automatic                                                           | `kubectl config use-context docker-desktop`            |
| Azure AKS      | `az aks get-credentials -g <RESOURCE-GROUP> -n <CLUSTER>`                   | `kubectl config use-context <CONTEXT>`                 |
| AWS EKS        | `aws eks update-kubeconfig --region <REGION> --name <CLUSTER>`              | `kubectl config use-context <CONTEXT>`                 |
| Google GKE     | `gcloud container clusters get-credentials <CLUSTER> --location <LOCATION>` | `kubectl config use-context <CONTEXT>`                 |
| VMware Tanzu   | `tanzu cluster kubeconfig get <CLUSTER> --admin`                            | `kubectl config use-context <CLUSTER>-admin@<CLUSTER>` |

## 1. Common commands for every Kubernetes cluster

First, see all clusters/contexts available on your machine:

```bash
kubectl config get-contexts
```

Example:

```text
CURRENT   NAME
*         docker-desktop
          my-aks-cluster
          arn:aws:eks:us-east-1:123456789:cluster/my-eks
          gke_my-project_us-central1_my-gke
          tkg-dev-admin@tkg-dev
```

See only the current context:

```bash
kubectl config current-context
```

Switch:

```bash
kubectl config use-context docker-desktop
```

Then test:

```bash
kubectl cluster-info
kubectl get nodes
kubectl get namespaces
```

The `*` from:

```bash
kubectl config get-contexts
```

shows the context currently being used.

## 2. Docker Desktop Kubernetes

Docker Desktop normally creates the context automatically when Kubernetes is enabled.

Switch to Docker:

```bash
kubectl config use-context docker-desktop
```

Verify:

```bash
kubectl config current-context
kubectl get nodes
```

Typical result:

```text
NAME             STATUS   ROLES           AGE   VERSION
docker-desktop   Ready    control-plane
```

Docker's current documentation specifically uses `docker-desktop` as the context name. ([Docker Documentation][1])

If you're using **kind** inside Docker instead:

```bash
kind get clusters
```

Example:

```text
kind
```

Then:

```bash
kubectl config use-context kind-kind
```

For a named kind cluster:

```bash
kind create cluster --name dev
```

the context is generally:

```bash
kubectl config use-context kind-dev
```

## 3. Microsoft Azure AKS

First authenticate:

```bash
az login
```

Optionally see subscriptions:

```bash
az account list -o table
```

Select one:

```bash
az account set --subscription "<SUBSCRIPTION-ID-OR-NAME>"
```

See AKS clusters:

```bash
az aks list -o table
```

Download/merge cluster credentials:

```bash
az aks get-credentials \
  --resource-group myResourceGroup \
  --name myAKSCluster
```

Azure merges the credentials into `~/.kube/config` by default. ([Microsoft Learn][2])

Then:

```bash
kubectl config get-contexts
```

Usually you can switch with something like:

```bash
kubectl config use-context myAKSCluster
```

Verify:

```bash
kubectl get nodes
```

### Useful AKS overwrite

If the context already exists:

```bash
az aks get-credentials \
  --resource-group myResourceGroup \
  --name myAKSCluster \
  --overwrite-existing
```

## 4. AWS EKS

First verify your AWS identity:

```bash
aws sts get-caller-identity
```

List clusters:

```bash
aws eks list-clusters --region us-east-1
```

Add the cluster to your kubeconfig:

```bash
aws eks update-kubeconfig \
  --region us-east-1 \
  --name my-eks-cluster
```

AWS merges the EKS configuration into `~/.kube/config` and makes the new EKS context current. ([AWS Documentation][3])

Check:

```bash
kubectl config current-context
```

It might look like:

```text
arn:aws:eks:us-east-1:123456789012:cluster/my-eks-cluster
```

Switch manually:

```bash
kubectl config use-context \
  arn:aws:eks:us-east-1:123456789012:cluster/my-eks-cluster
```

A much cleaner option is to create an alias:

```bash
aws eks update-kubeconfig \
  --region us-east-1 \
  --name my-eks-cluster \
  --alias aws-dev
```

Now switching is easy:

```bash
kubectl config use-context aws-dev
```

AWS supports `--alias` specifically for this purpose. ([AWS Documentation][3])

Then:

```bash
kubectl get nodes
```

### Using an AWS profile

```bash
aws eks update-kubeconfig \
  --profile dev \
  --region us-east-1 \
  --name my-eks-cluster \
  --alias aws-dev
```

## 5. Google Cloud GKE

Authenticate:

```bash
gcloud auth login
```

Set project:

```bash
gcloud config set project my-project
```

List clusters:

```bash
gcloud container clusters list
```

Get credentials:

```bash
gcloud container clusters get-credentials my-gke-cluster \
  --location us-central1
```

For a zonal cluster you might instead use:

```bash
gcloud container clusters get-credentials my-gke-cluster \
  --zone us-central1-a
```

Google's command creates the kubeconfig entry and also switches `kubectl` to that context. ([Google Cloud Documentation][4])

View it:

```bash
kubectl config get-contexts
```

A GKE context usually looks similar to:

```text
gke_my-project_us-central1_my-gke-cluster
```

Switch:

```bash
kubectl config use-context \
  gke_my-project_us-central1_my-gke-cluster
```

Verify:

```bash
kubectl get nodes
```

## 6. VMware Tanzu Kubernetes

VMware/Broadcom environments vary somewhat depending on whether you're using Tanzu Kubernetes Grid, vSphere with Tanzu, or Cloud Director.

For a traditional Tanzu workload cluster, retrieve its kubeconfig:

```bash
tanzu cluster kubeconfig get my-cluster --admin
```

Then:

```bash
kubectl config get-contexts
```

A common context format is:

```text
my-cluster-admin@my-cluster
```

Switch:

```bash
kubectl config use-context my-cluster-admin@my-cluster
```

Then:

```bash
kubectl get nodes
```

This is the established Tanzu pattern, although the exact credential command can differ by Tanzu/vSphere release. ([VMware Blogs][5])

For environments where the administrator gives you a kubeconfig file, you can use it directly:

```bash
export KUBECONFIG=~/Downloads/tanzu-kubeconfig.yaml
```

Then:

```bash
kubectl config get-contexts
kubectl config use-context <context-name>
```

## A good naming scheme

When working across all five environments, I recommend creating short context names such as:

```text
docker
azure-dev
aws-dev
gcp-dev
vmware-dev
```

For example, rename an existing context:

```bash
kubectl config rename-context docker-desktop docker
```

For AKS:

```bash
kubectl config rename-context myAKSCluster azure-dev
```

For GKE:

```bash
kubectl config rename-context \
  gke_my-project_us-central1_my-cluster \
  gcp-dev
```

For VMware:

```bash
kubectl config rename-context \
  my-cluster-admin@my-cluster \
  vmware-dev
```

AWS can create the nice name directly:

```bash
aws eks update-kubeconfig \
  --region us-east-1 \
  --name my-cluster \
  --alias aws-dev
```

Then your normal workflow becomes very simple:

```bash
# Show everything
kubectl config get-contexts

# Local Docker
kubectl config use-context docker

# Azure
kubectl config use-context azure-dev

# AWS
kubectl config use-context aws-dev

# Google
kubectl config use-context gcp-dev

# VMware
kubectl config use-context vmware-dev

# Always verify before changing anything
kubectl config current-context
kubectl get nodes
```

A particularly good habit before running `kubectl apply`, `helm install`, or especially `kubectl delete` is:

```bash
kubectl config current-context
```

That prevents accidentally running a command against AWS production when you thought you were working on Docker Desktop.
