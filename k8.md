Here’s the expanded cheat sheet with **login/authentication**, **getting the cluster into kubeconfig**, **switching context**, and **checking nodes, pods, services, and deployments**.

| Platform       | Login                              | Get kubeconfig/context                          | Typical context             |
| -------------- | ---------------------------------- | ----------------------------------------------- | --------------------------- |
| Docker Desktop | None                               | Automatic                                       | `docker-desktop`            |
| Azure AKS      | `az login`                         | `az aks get-credentials ...`                    | cluster name                |
| AWS EKS        | `aws sso login` or AWS credentials | `aws eks update-kubeconfig ...`                 | ARN or alias                |
| Google GKE     | `gcloud auth login`                | `gcloud container clusters get-credentials ...` | `gke_...`                   |
| VMware Tanzu   | Tanzu/vSphere login varies         | `tanzu cluster kubeconfig get ...`              | `<cluster>-admin@<cluster>` |

## Common Kubernetes commands

These work the same after you connect to **Docker, Azure, AWS, GCP, or VMware**:

```bash
# See all Kubernetes contexts
kubectl config get-contexts

# See current context
kubectl config current-context

# Switch cluster
kubectl config use-context <CONTEXT>

# Check connection
kubectl cluster-info

# Check nodes
kubectl get nodes

# More node information
kubectl get nodes -o wide

# Check deployments
kubectl get deployments

# Check deployments in every namespace
kubectl get deployments -A

# Check pods
kubectl get pods

# Pods in every namespace
kubectl get pods -A

# More pod information
kubectl get pods -o wide

# Services
kubectl get services

# Everything in current namespace
kubectl get all

# Everything across namespaces
kubectl get all -A
```

A very useful troubleshooting sequence is:

```bash
kubectl config current-context
kubectl cluster-info
kubectl get nodes
kubectl get deployments -A
kubectl get pods -A
kubectl get services -A
```

Enable Kubernetes in Docker Desktop first.

```bash
kubectl config get-contexts
```

```bash
kubectl config use-context docker-desktop
```


```bash
kubectl get deployments
kubectl get deployments -A

kubectl get pods
kubectl get pods -A

kubectl get services
```

For Docker Desktop you should typically see a node similar to:

```text
docker-desktop   Ready
```

```bash
kind get clusters
```

Then:

```bash
kubectl config use-context kind-kind
kubectl get nodes
```

```bash
kind create cluster --name dev
```

switch with:

## Login

Interactive browser login:

```bash
az login
```

Check which Azure account you're using:

```bash
az account show
```

```bash
az account list -o table
```

```bash
az account set \
```

Verify:


```bash
az aks list -o table
```

## Add AKS to kubeconfig

```bash
az aks get-credentials \
  --resource-group myResourceGroup \
  --name myAKSCluster
```

Azure merges these credentials into your kubeconfig by default. ([Microsoft Learn][2])

If it already exists:

```bash
az aks get-credentials \
  --resource-group myResourceGroup \
  --name myAKSCluster \
  --overwrite-existing
```

## Switch context

```bash
kubectl config get-contexts
```

Then:

```bash
kubectl config use-context myAKSCluster
```

## Check AKS

```bash
kubectl config current-context
```


Detailed deployment information:


# 3. AWS EKS

AWS has two common login approaches.

## Option A — AWS SSO / IAM Identity Center

First-time setup:

```bash
aws configure sso
```

Login:

```bash
aws sso login
```

Or with a profile:

```bash
aws sso login --profile dev
```

AWS CLI caches the IAM Identity Center access token after login. ([AWS Documentation][3])

Check identity:

```bash
aws sts get-caller-identity
```

With a profile:

```bash
aws sts get-caller-identity --profile dev
```

## Option B — normal AWS credentials

Configure:

```bash
aws configure
```

Enter:

```text
AWS Access Key ID:
AWS Secret Access Key:
Default region:
Default output format:
```

Then test:

```bash
aws sts get-caller-identity
```

For human users, SSO/IAM Identity Center is generally preferable to long-lived access keys.

## List EKS clusters

```bash
aws eks list-clusters \
  --region us-east-1
```

With profile:

```bash
aws eks list-clusters \
  --region us-east-1 \
  --profile dev
```

## Add EKS kubeconfig

```bash
aws eks update-kubeconfig \
  --region us-east-1 \
  --name my-eks-cluster
```

AWS documents that this creates or updates the kubeconfig and uses the AWS identity available through the CLI credential chain. ([AWS Documentation][4])

I recommend giving the cluster a short alias:

```bash
aws eks update-kubeconfig \
  --region us-east-1 \
  --name my-eks-cluster \
  --alias aws-dev
```

Using an AWS profile:

```bash
aws eks update-kubeconfig \
  --profile dev \
  --region us-east-1 \
  --name my-eks-cluster \
  --alias aws-dev
```

## Switch

```bash
kubectl config use-context aws-dev
```

## Check AWS EKS

```bash
kubectl config current-context

kubectl cluster-info

kubectl get nodes

kubectl get nodes -o wide

kubectl get deployments -A

kubectl get pods -A

kubectl get services -A
```

AWS also recommends basic connectivity checks such as `kubectl get svc`. ([AWS Documentation][5])

# Best quick health check

After logging into **any** cloud and switching context, I would run this sequence:

```bash
echo "=== CURRENT CLUSTER ==="
kubectl config current-context

echo "=== CLUSTER ==="
kubectl cluster-info

echo "=== NODES ==="
kubectl get nodes -o wide

echo "=== NAMESPACES ==="
kubectl get namespaces

echo "=== DEPLOYMENTS ==="
kubectl get deployments -A

echo "=== PODS ==="
kubectl get pods -A

echo "=== SERVICES ==="
kubectl get services -A
```

The most important safety check is always:

```bash
kubectl config current-context
```

before you run commands such as:

```bash
kubectl apply
kubectl delete
helm install
helm upgrade
```

That makes it much less likely that you accidentally modify **EKS/AKS/GKE production when you thought you were working on Docker Desktop**.

Yes — Azure **AKS**. The key idea is that every Kubernetes platform ultimately adds a **context** to your kubeconfig, normally `~/.kube/config`. After that, the universal command is:

```bash
kubectl config get-contexts
kubectl config use-context <CONTEXT-NAME>
```

### Kubernetes context cheat sheet

| Platform       | Add/get cluster credentials                                                 | Switch context                                         |
| -------------- | --------------------------------------------------------------------------- | ------------------------------------------------------ |
| Docker Desktop | Usually automatic                                                           | `kubectl config use-context docker-desktop`            |
| Azure AKS      | `az aks get-credentials -g <RESOURCE-GROUP> -n <CLUSTER>`                   | `kubectl config use-context <CONTEXT>`                 |
| AWS EKS        | `aws eks update-kubeconfig --region <REGION> --name <CLUSTER>`              | `kubectl config use-context <CONTEXT>`                 |
| Google GKE     | `gcloud container clusters get-credentials <CLUSTER> --location <LOCATION>` | `kubectl config use-context <CONTEXT>`                 |
| VMware Tanzu   | `tanzu cluster kubeconfig get <CLUSTER> --admin`                            | `kubectl config use-context <CLUSTER>-admin@<CLUSTER>` |

The `*` from:

## 4. AWS EKS

First verify your AWS identity:

```bash
aws sts get-caller-identity
```

List clusters:

```bash
aws eks list-clusters --region us-east-1
```

Add the cluster to your kubeconfig:

```bash
aws eks update-kubeconfig \
  --region us-east-1 \
  --name my-eks-cluster
```

AWS merges the EKS configuration into `~/.kube/config` and makes the new EKS context current. ([AWS Documentation][3])

Check:

```bash
kubectl config current-context
```

It might look like:

```text
arn:aws:eks:us-east-1:123456789012:cluster/my-eks-cluster
```

Switch manually:

```bash
kubectl config use-context \
  arn:aws:eks:us-east-1:123456789012:cluster/my-eks-cluster
```

A much cleaner option is to create an alias:

```bash
aws eks update-kubeconfig \
  --region us-east-1 \
  --name my-eks-cluster \
  --alias aws-dev
```

Now switching is easy:

```bash
kubectl config use-context aws-dev
```

AWS supports `--alias` specifically for this purpose. ([AWS Documentation][3])

Then:

```bash
kubectl get nodes
```

### Using an AWS profile

```bash
aws eks update-kubeconfig \
  --profile dev \
  --region us-east-1 \
  --name my-eks-cluster \
  --alias aws-dev
```

## A good naming scheme

When working across all five environments, I recommend creating short context names such as:

```text
docker
azure-dev
aws-dev
gcp-dev
vmware-dev
```

For example, rename an existing context:

```bash
kubectl config rename-context docker-desktop docker
```

For AKS:

```bash
kubectl config rename-context myAKSCluster azure-dev
```

For GKE:

```bash
kubectl config rename-context \
  gke_my-project_us-central1_my-cluster \
  gcp-dev
```

For VMware:

```bash
kubectl config rename-context \
  my-cluster-admin@my-cluster \
  vmware-dev
```

AWS can create the nice name directly:

```bash
aws eks update-kubeconfig \
  --region us-east-1 \
  --name my-cluster \
  --alias aws-dev
```

Then your normal workflow becomes very simple:

```bash
# Show everything
kubectl config get-contexts

# Local Docker
kubectl config use-context docker

# Azure
kubectl config use-context azure-dev

# AWS
kubectl config use-context aws-dev

# Google
kubectl config use-context gcp-dev

# VMware
kubectl config use-context vmware-dev

# Always verify before changing anything
kubectl config current-context
kubectl get nodes
```

A particularly good habit before running `kubectl apply`, `helm install`, or especially `kubectl delete` is:

```bash
kubectl config current-context
```

That prevents accidentally running a command against AWS production when you thought you were working on Docker Desktop.
