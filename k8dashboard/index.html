Go live with a real cluster

Browsers block pages from calling other servers unless the server allows it, so the safest, simplest way to use Live mode is to let kubectl proxy serve this page and the API from the same address. That works on every hosting option below.

  1. Install kubectl and sign in to your cluster

    Use the sign-in command shown for your hosting choice:

  2. Save this dashboard as index.html inside an empty folder called k8s-dash

    If the download button is hidden, use “Copy page HTML” and paste it into a new file with a text editor.

  3. Start the proxy and serve the folder

    kubectl proxy --port=8001 --www=./k8s-dash --www-prefix=/ui/

    The proxy signs every request with your kubeconfig, so no token is needed.

  4. Open http://localhost:8001/ui/, choose Live, leave the URL blank, and click Connect

    Because the page and the API share one address, the browser lets them talk.

Versions & upgrades

Kubernetes ships three minor versions a year and supports each for about 14 months. Staying inside the supported window, keeping every part within the allowed “skew”, and using a matching Helm are the three checks that prevent most upgrade surprises.

Access control

Who may do what in this dashboard. A role is a bundle of permissions; a binding gives a role to a user or a group, everywhere or only in certain namespaces. That is exactly how Kubernetes RBAC works too, so the “My access” tab shows your dashboard role translated into Kubernetes YAML.

These rules live in this browser's local storage. They stop mistakes and teach how RBAC works, but anyone with this file and the browser's developer tools can change them. Real protection is Kubernetes RBAC on the credential you connect with: sign in with OIDC so each person uses their own token, or use a read-only kubeconfig.

What I can do

OIDC (OpenID Connect)

        
Sign in through Keycloak, Dex, Okta, Auth0, Microsoft Entra ID, Google or any OpenID provider. Groups from the ID token map to roles through bindings, and the same token can be used to talk to Kubernetes — so the cluster enforces the real rules.

        

          
          

          

          

          

          

          

          

            

            

          

          

          
          
          

          

          
Kubernetes API server settings for this provider
Self-managed: save as a file and start kube-apiserver with --authentication-config=/etc/kubernetes/auth.yaml. Managed clouds have a switch for it: EKS “identity provider configs”, GKE “Identity Service”, AKS “Microsoft Entra ID integration”, IBM Cloud/OpenShift “identity providers”.

        

      


      

        
LDAP / Active Directory

        
Browsers cannot speak LDAP directly, so the directory is reached through a helper. Choose one: an identity provider (Dex or Keycloak) that reads the directory and issues OIDC tokens, or a small auth service URL that checks the password against LDAP and returns the user's groups.

        

          
          

          

          

          

          

            

            

            

            

            

            

            

            

          

          

          

          
What the auth service must do (service mode)
The dashboard sends POST {authUrl} with JSON {"username": "...", "password": "..."} and expects JSON back: {"user": "maria", "groups": ["dev-team-a"], "token": "optional Kubernetes bearer token"}, or HTTP 401 when the password is wrong. Run it on the same address as this page (or allow CORS for it) and always over HTTPS. Any small program that can bind to LDAP with the user's own credentials can do this; Dex or Keycloak are the maintained alternatives.

Learn: step by step

    
  

  
Kubernetes (say “koo-ber-NET-eez”, or K8s, because there are 8 letters between the K and the s) is a program that runs your apps across many computers and keeps them running. Think of it as a school: the front office (control plane) keeps the schedule, classrooms (nodes) hold desks (pods), and each desk seats a student (container). Follow the numbered steps to learn by doing.


  

    

      
Your first 10 minutes (Demo mode)

      
    
        
  1. Pick a hosting option
    Use the Hosting menu at the top. The demo cluster changes shape to match: managed clouds hide the control plane, local clusters show one node, OpenShift shows control-plane nodes.
    2. 
        
  2. Read the cluster map
    Each box is a node; each square is a pod. One square is red: an app is failing. Hover over it to see why.
    3. 
        
  3. Check the control plane
    Green means the brain is healthy. On managed clouds the provider runs it for you, so some rows say “managed”.
    4. 
        
  4. Find the broken pod
    In Pods, look for ImagePullBackOff. Click “Events” to see the reason: the image name has a typo, so the node cannot download it.
    5. 
        
  5. Fix it
    Commands → Configure → “Change the container image”: choose reports and set the image to nginx:1.29.1. Watch the square turn green.
    6. 
        
  6. Scale up
    Scale web to 4 replicas. New squares appear, go yellow (starting) and then green (running).
    7. 
        
  7. Delete a pod on purpose
    Delete any web pod. Kubernetes notices there are fewer than you asked for and creates another one. That is “self-healing”.
    8. 
        
  8. Read logs
    Logs → pick a web pod → Fetch. Type error in the filter box to find problems fast.
    9. 
        
  9. Check your versions
    Versions & upgrades → “Fill from cluster” → “Check for conflicts”. Then build an upgrade plan to the newest release.
    10. 
        
  10. Try access control
    Sign out (top bar) and sign in as carol (a practice identity in the “viewers” group). Try to delete a pod: the button is locked and the attempt shows up in Access control → Audit log. Sign back in as admin and give the group a bigger role in Bindings.
    11. 
        
  11. Go live
    When you are comfortable, follow “Go live with a real cluster” in the Connect section. Everything you practised works the same way.
    12. 
      

    


    

      

        
How this dashboard talks to Kubernetes

        
Everything goes through one door: the API server. It speaks HTTP and JSON, exactly like a website's back end.

        
GET    /version                                  → which Kubernetes version?
GET    /readyz?verbose                           → is the control plane ready?
GET    /api/v1/nodes                             → list nodes
GET    /api/v1/pods                              → list pods (all namespaces)
GET    /apis/apps/v1/deployments                 → list deployments
GET    /api/v1/services                          → list services
GET    /api/v1/namespaces/default/pods/web-1/log → read a pod's logs
PATCH  /apis/apps/v1/namespaces/default/deployments/web/scale
                                                 → change replicas
DELETE /api/v1/namespaces/default/pods/web-1     → delete a pod

        
Core things (pods, nodes, services) live under /api/v1. Everything else is grouped, like /apis/apps/v1 for Deployments. The group and version are exactly what you write as apiVersion: in YAML.
